## Why

El detalle web de una factura ya muestra la clave SAT de producto/servicio (cruda), IEPS y subtotal por línea, pero el PDF —tanto el borrador de prefactura como el real ya timbrado, que comparten el mismo componente `InvoiceDocumentPdf.tsx`— carece de las tres. El modal de prefactura, a su vez, no muestra forma/método de pago pese a que el PDF sí los tiene. Esta asimetría entre las 4 superficies de render (modal prefactura, PDF prefactura, web factura, PDF factura) dificulta usar la prefactura como control de calidad antes de una acción irreversible, y dificulta validar visualmente que el PDF descargado corresponde a lo que la pantalla ya mostró — el mismo tipo de problema de fondo que causó el bug real corregido esta madrugada (`fix-billing-issuer-fiscal-regime-overflow`). El catálogo SAT de clave de producto/servicio (`SatProductServiceCode`/`SatCodeRepository`) ya existe en el proyecto con el mismo contrato que los catálogos de régimen fiscal y uso CFDI ya resueltos — no hay que crear infraestructura nueva, sólo aplicar el patrón ya vigente a un cuarto campo.

Por separado, `TicketSettings` (Configuración > Ticket de venta) no captura Código Postal como campo propio, así que la cascada de resolución del emisor (`resolveIssuerFiscalData.ts`) deja `zipCode` sin su 3er nivel de respaldo — a diferencia de `rfc`/`legalName`/`fiscalRegime`/`address`, que sí caen hasta Ticket de venta cuando el CSD manager está vacío. Esto deja incompleta, sólo para ese campo, la cascada "CSD primero, ticket de venta como respaldo" que el usuario pidió confirmar — el resto de la cascada ya la cumple.

Finalmente, dado que la sesión anterior con este mismo usuario reveló un bug de producción real detrás de una implementación que parecía correcta en el código pero nunca se probó contra datos reales, este cambio exige explícitamente verificación en vivo (no sólo tests unitarios) como criterio de "hecho".

## What Changes

- `InvoiceDocumentPdf.tsx`: la tabla de conceptos gana columna de clave SAT (código + descripción resuelta), columna IEPS% por línea, y columna Subtotal por línea — mismas columnas que ya tiene la web. Como este componente es compartido, el cambio corrige a la vez el PDF de prefactura y el PDF de factura final.
- Resolución server-side de la descripción de `satProductCode` por línea, reutilizando `SatCodeRepository`/`SearchSatCodesUseCase` (ya existentes) con el mismo patrón que régimen fiscal/uso CFDI: en `FakeFacturamaGateway.download` (factura final), `BillingController.previewPdf` (prefactura PDF) y `BillingController.getById` (factura web).
- `InvoicePreviewModal.tsx`: gana sección de Forma/Método de pago (con descripción) y las mismas 3 columnas por línea (clave SAT, IEPS%, Subtotal), resueltas client-side reutilizando el patrón ya vigente de `resolveFiscalRegimeDescription`/`resolveCfdiUseDescription`.
- `TicketSettings` gana el campo `businessZipCode` (nullable, `VarChar(5)`, mismo patrón que `businessPhone`) en todas sus capas (dominio, puerto, use case, repositorios, controller, tipos de frontend, formulario) — migración Prisma incluida.
- `resolveIssuerFiscalData.ts`: `zipCode` gana su 3er nivel de cascada (`ticket?.businessZipCode`), completando para los 5 campos del emisor el comportamiento "CSD primero, ticket de venta como respaldo" que los otros 4 campos ya tienen.
- `branchName` del emisor se agrega a la factura final (web vía `InvoiceDto`/`toInvoiceDto`, resuelto en `BillingController.getById` con el `BillingLookupService` ya inyectado; PDF vía `FacturamaInvoiceSnapshot`/`DownloadInvoiceFileUseCase`, que gana `BillingLookupService` como nueva dependencia) — hoy sólo aparece en la prefactura.
- Verificación en vivo obligatoria (servidor dev + datos reales, no sólo `npm test`) antes de dar el cambio por terminado.
