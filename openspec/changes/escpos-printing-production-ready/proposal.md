**Nota:** el gap se dividió en 3 historias independientes (INVEST) porque son entregables desacoplados con dueños distintos: la 1 es frontend/panel, la 2 es empaquetado/DevOps del agente sin tocar el panel, la 3 es verificación manual del usuario con hardware físico. Ninguna bloquea la implementación de las otras, aunque la 3 solo se puede *ejecutar* con 1 y 2 ya desplegadas.

## Why

El bug de "hoja en blanco sobrante" al imprimir tickets vía navegador (`openspec/changes/refine-thermal-ticket-print-layout`, sin archivar aún) es estructural: `window.print()` es un pipeline *page-based* — declara un `@page` de alto estimado (`computeTicketPageHeightMm`) y la impresora corta ahí exista o no contenido, dejando siempre un colchón de seguridad visible como blanco. ESC/POS es *line-based* — el agente local manda línea por línea y corta justo donde termina el contenido real, eliminando el problema de raíz sin necesitar estimar ningún alto.

El motor ESC/POS ya existe completo (`add-escpos-ticket-printing`, 24/24 tareas: API de configuración por sucursal, bifurcación en `TicketPreviewPage`, agente de referencia en `tools/escpos-print-agent`), pero **no es operable en producción**: falta la pantalla para que un admin configure la sucursal sin tocar la API a mano, el agente no sobrevive un reinicio de la PC de caja (no es un servicio), y nunca se probó contra una impresora térmica física. Sin estas 3 piezas, "empujar a ESC/POS" como resolución del bug queda en el papel.

## What Changes

- Agrega un formulario de configuración de impresión (printMode/agentUrl/printerHost/printerPort) en el flujo de edición de sucursal de `/catalogs/branches`, gateado por `settings:read`/`settings:write`, consumiendo el endpoint ya existente `GET/PATCH /api/v1/admin/branches/:id/printer-config`.
- Empaqueta `tools/escpos-print-agent/index.js` como ejecutable standalone (`pkg` o `nexe`) y lo registra como servicio de Windows con auto-arranque (`node-windows` o `nssm`), sin alterar el contrato HTTP `POST /print`.
- Documenta y ejecuta (a cargo del usuario, con hardware real) la verificación end-to-end contra una EPSON TM-T20II física, cerrando la limitación conocida del README del agente.
- Actualiza el canonical `escpos-ticket-printing` para reflejar que la configuración por sucursal es alcanzable desde una pantalla del panel (no solo vía API cruda) y que el agente local es un servicio persistente, no un proceso manual.

### Modified Capabilities

## Impact

- **Frontend nuevo**: `app/(private)/catalogs/branches/_blocks/` (sección/tab de configuración de impresión dentro de `BranchEditModal` o modal dedicado), `app/(private)/catalogs/branches/_logic/` (hook de mutación + servicio HTTP para `printer-config`).
- **Sin cambios de backend**: `src/modules/settings/` ya expone el endpoint completo; no se tocan use cases, repos ni el controller salvo que la verificación de tasks encuentre un gap puntual.
- **`tools/escpos-print-agent/`**: se agrega empaquetado (`package.json` scripts, config de `pkg`/`nexe`) y script/documentación de instalación como servicio de Windows. El `index.js` (lógica ESC/POS) no cambia de comportamiento.
- **Spec canonical**: `openspec/specs/escpos-ticket-printing/spec.md` — delta en el requirement de configuración + nuevo requirement de persistencia del agente.
- **Verificación física**: depende de hardware del usuario (EPSON TM-T20II) — no ejecutable por el agente de IA en esta sesión.
