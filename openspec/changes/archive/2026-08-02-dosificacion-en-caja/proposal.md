Nota: se dividió en 3 historias porque cubren capas independientes y testeables por separado — historia 1 es el caso de uso de negocio (venta), historia 2 es la corrección de inventario transversal a 4 flujos (el riesgo real del cambio), historia 3 es la UI del selector. Las tres se implementan en el mismo change dado que están fuertemente acopladas (sin historia 2, la 1 introduce un bug de stock; sin la 3, la 1 no es alcanzable desde la UI).

## Why

Feedback de producción (#32) reporta que no se puede vender por dosificación desde caja en tiempo real. El catálogo ya modela dosificaciones (`ProductDosification`: `numParts`, `computedUnitPrice = basePrice/numParts*1.07`) desde un change anterior, pero el POS sólo conoce `ProductPrice` — no hay puente entre ambos conceptos en el flujo de venta. Mapeado el código real (`CreateSaleUseCase`, `CancelSaleUseCase`/`PrismaSaleRepository.cancel`, `EditCompletedSaleUseCase`/`replaceItemsAndRecalculate`, `PrismaReturnRepository.createWithItems`/`markCancelled`), se confirmó que los 4 flujos que mueven `branch_inventory.quantity` a partir de una línea de venta usan `item.quantity` directo — si una línea representa "partes de una dosificación" en vez de "unidades del producto base", los 4 flujos necesitan dividir entre `numParts` para no descontar/restaurar mal el stock. Es la feature de mayor alcance de esta sesión (confirmado con el usuario antes de proceder), pero acotada: no requiere modelar contenedores físicos abiertos, sólo aritmética de fracción sobre el modelo de inventario Decimal(14,4) que el sistema ya usa para venta a granel.

## What Changes

- `SaleItemInput` (compartido por `CreateSaleRequest`/`EditCompletedSaleRequest`) acepta `dosificationId?: string` como alternativa a `productPriceId` (mutuamente excluyentes, exactamente uno de los dos por línea).
- `PosLookupService` agrega `getDosificationForSale(id)` retornando `{id, productId, name, numParts, isActive, basePrice: number | null}` (basePrice = precio default del producto; `null` si no existe, análogo a `requiresDefaultPrice` del lado catálogo).
- `CreateSaleUseCase`/`EditCompletedSaleUseCase`: por línea, si trae `dosificationId`, resuelve la dosificación en vez del precio, valida activa + `basePrice !== null`, calcula `unitPrice` vía `DosificationPriceCalculator.computeUnitPrice(basePrice, numParts)` (servicio ya existente, reusado), snapshotea `dosificationId`, `dosificationNameSnapshot` (en `priceNameSnapshot`, mismo campo que ya usan las líneas de precio) y `numPartsSnapshot`.
- **Migración**: `sale_items` y `return_items` agregan `dosification_id TEXT NULL` (FK a `product_dosifications`, `ON DELETE SET NULL`) y `num_parts_snapshot INT NULL`.
- Nuevo helper de dominio puro `inventoryQuantityOf(quantity, numPartsSnapshot)` = `numPartsSnapshot ? quantity / numPartsSnapshot : quantity`, aplicado en los 5 puntos que hoy llaman `recordInventoryMovement` con `item.quantity` directo: `PrismaSaleRepository.createCompleted`, `createCompletedFromQuote`, `cancel` (restore), `replaceItemsAndRecalculate` (restore + apply), y `PrismaReturnRepository.createWithItems`/`markCancelled`.
- `CreateReturnUseCase` propaga `numPartsSnapshot` del `SaleItem` original al `ReturnItem` snapshot (mismo patrón que ya usa para `priceNameSnapshot`/`productCodeSnapshot`).
- POS UI: `PriceTierPicker` (o extensión del mismo diálogo) lista dosificaciones activas del producto junto a los precios de catálogo, deshabilitando las que tienen `requiresDefaultPrice: true`. Selecciona `dosificationId` en vez de `productPriceId` al confirmar.
- Sale detail (`SaleItemsTable`) y ticket muestran la dosificación vendida cuando aplica (reusa `priceNameSnapshot` ya renderizado, sin cambio de UI adicional salvo quizás una etiqueta distintiva).

## Capabilities

### New Capabilities

- `pos-ui`: no existía spec formal para la capa de UI del POS (catálogo/carrito/selector de precio) pese a tener código y tests — se crea ahora, cubriendo únicamente el diálogo de selección de precio/dosificación al agregar un producto al carrito (alcance de este change; no se documenta retroactivamente todo el POS).

### Modified Capabilities

- `pos-api`: `Sale aggregate model` y `Create sale (atomic emission)` se extienden con líneas de dosificación (columnas nuevas, validación, cálculo de inventario fraccionario). Se agrega tratamiento equivalente a `Cancel sale` y `Edit completed sale`.
- `returns-api`: `Return aggregate model`, `Create return (atomic registration)` y `Cancel return` se extienden para propagar y usar `numPartsSnapshot` en el cálculo de inventario.
