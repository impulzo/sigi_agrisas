## Historia de Usuario

| # | Rol | Tarea | Motivo | Criterios de Aceptación | Criterios de Seguridad |
|---|---|---|---|---|---|
| 1 | Administrador | Como Administrador, quiero crear un usuario sin capturar su contraseña para que el sistema le envíe automáticamente un correo con el que él mismo la establezca | Elimina el riesgo de que el admin conozca/maneje contraseñas ajenas y evita fricción de comunicarla por canales inseguros | - Given el admin llena nombre/email/roles/sucursal (sin campo password) en `/users`, When confirma creación, Then el usuario se crea con `passwordHash=null` y HTTP 201<br>- Given la creación fue exitosa, When se dispara el correo de "establecer contraseña", Then el envío nunca bloquea ni revierte la creación aunque el SMTP falle (se registra el error, no se expone al admin)<br>- Given el email ya existe, When el admin intenta crear con ese email, Then 409 igual que hoy (sin cambio de esa regla) | - Password nunca viaja en el body de creación (elimina superficie de captura/logueo de contraseñas por el admin)<br>- Endpoint sigue exigiendo permiso `users:write`<br>- El correo de invitación se envía solo a la dirección registrada del nuevo usuario, nunca a un destino arbitrario del request |
| 2 | Usuario invitado / con contraseña por restablecer | Como usuario que recibió el enlace por correo, quiero establecer mi propia contraseña desde ese enlace para poder iniciar sesión sin que el administrador la haya visto nunca | Le da al usuario control exclusivo sobre su credencial y cumple el requisito de que el admin jamás la maneje | - Given un token válido y no usado, When el usuario envía una contraseña de al menos 8 caracteres, Then se guarda el hash, el token queda consumido y el usuario inicia sesión automáticamente<br>- Given el token ya fue usado o no existe, When se reintenta el enlace, Then error explícito (token inválido) sin revelar si el email existe<br>- Given el token expiró (24h), When se intenta usar, Then error de expirado, distinto al de "inválido", con opción de pedir un reenvío<br>- Given un usuario con `passwordHash=null` intenta hacer login normal antes de completar el flujo, When envía email+password, Then 403 explícito indicando que debe establecer su contraseña primero (no un genérico "credenciales inválidas") | - Token de un solo uso, aleatorio de alta entropía, almacenado solo como hash (nunca en texto plano en BD)<br>- Expiración dura (24h) aplicada server-side, no solo en UI<br>- Al emitir un nuevo token para el mismo usuario se invalidan los anteriores (evita múltiples enlaces vivos)<br>- Endpoint público (`/api/v1/auth/set-password`) validado y accesible sin JWT, pero sin filtrar existencia de usuarios en los mensajes de error |
| 3 | Administrador | Como Administrador, quiero reenviar el correo de establecer/restablecer contraseña desde la edición de un usuario en vez de poder escribirla yo mismo, para mantener la regla de que el admin nunca maneja contraseñas también al editar | Cierra el mismo problema de seguridad/higiene de credenciales también en el ciclo de vida posterior a la creación (usuario que perdió su enlace o quiere resetear) | - Given un usuario existente, When el admin abre editar y pulsa "Enviar correo para establecer/restablecer contraseña" (con confirmación), Then se genera un nuevo token (invalidando los previos) y se reenvía el correo<br>- Given el envío de correo falla (SMTP caído), When el admin dispara el reenvío explícito, Then el admin sí ve un error claro (a diferencia del envío silencioso en creación), porque aquí la acción es intencional y necesita feedback<br>- Given el modal de edición, When se revisa el formulario, Then no existe ningún campo de contraseña editable, sólo el botón de reenvío | - Acción protegida por el mismo permiso `users:write` ya existente (sin nuevo permiso)<br>- El admin no puede auto-dispararse el reenvío para sí mismo de forma que filtre nada sensible (el token nunca se muestra en la respuesta HTTP, solo se envía por correo)<br>- No expone `passwordHash` ni el token crudo en ningún response de la API |

Nota: la feature original se dividió en 3 historias porque mezclaba tres actores/momentos distintos con criterios propios — creación (admin, sin password), autoservicio de establecer contraseña (usuario, vía token) y reenvío en edición (admin, sin editar password directo). El caso "login bloqueado si no ha establecido password" se dejó como edge case dentro de la historia 2 por ser la misma mecánica de token, no un flujo independiente.

## Why

Hoy el admin captura la contraseña del usuario en texto plano al crearlo (`UserEditModal.tsx`) y no tiene forma de cambiarla salvo recreándola — el sistema le exige conocerla, exactamente lo contrario del principio de que las credenciales las controla solo su dueño. Al no existir ningún mecanismo de token de un solo uso ni infraestructura de "olvidé mi contraseña" en el repo, este cambio construye ese mecanismo desde cero, reutilizando el `MailerPort`/`NodemailerMailer` ya usado por facturación y notificaciones, y el `PasswordHasher`/`Password` VO ya usados por el módulo `auth`. El resultado: el admin deja de tener contacto con contraseñas tanto al crear como al editar usuarios; el usuario las establece siempre vía un enlace de un solo uso que expira.

## What Changes

- `POST /api/v1/admin/users` deja de aceptar/exigir `password`; el usuario se crea con `passwordHash=null` y dispara (best-effort, sin bloquear la creación) el envío de un correo de "establecer contraseña".
- Nuevo mecanismo de token de un solo uso: tabla `password_setup_tokens` (hash del token, expiración 24h, consumo único, invalidación de tokens previos al reemitir).
- Nuevo endpoint público `POST /api/v1/auth/set-password` — completa el establecimiento de contraseña con el token del correo, hashea y persiste, y hace auto-login (emite access+refresh tokens) igual que el login normal.
- Nuevo endpoint admin `POST /api/v1/admin/users/:id/resend-set-password-email` — reemplaza cualquier posibilidad de editar la contraseña directamente; el admin solo puede reenviar el correo (permiso `users:write`, mismo que ya protege el módulo).
- `PATCH /api/v1/admin/users/:id` no cambia (ya no exponía password; se mantiene así explícitamente).
- **BREAKING**: `users.password_hash` pasa de `String` a `String?` en el schema — usuarios creados desde ahora pueden no tener contraseña hasta completar el flujo; `POST /api/v1/auth/login` para esos usuarios responde 403 `PasswordNotSet` en vez de intentar comparar contra un hash inexistente.
- UI: `UserEditModal` pierde el campo password en modo creación; en modo edición gana la acción "Enviar correo para establecer/restablecer contraseña" con confirmación. Nueva página pública `/auth/set-password`.

## Capabilities

### New Capabilities
- `password-setup`: emisión, expiración y consumo único de tokens de establecimiento de contraseña; endpoint `POST /api/v1/auth/set-password` con auto-login.

### Modified Capabilities
- `admin-users`: el requirement "Create user" deja de exigir `password` en el body y pasa a disparar el correo de invitación; nuevo requirement "Resend set-password email" para `POST /admin/users/:id/resend-set-password-email`.
- `user-auth`: el requirement "User login" gana el escenario de `passwordHash` nulo → 403 `PasswordNotSet`.
- `users-ui`: el modal de creación de usuario pierde el campo de contraseña; el modal de edición gana la acción de reenvío de correo.

- **Prisma**: `prisma/schema.prisma` (`User.passwordHash` → nullable, nuevo modelo `PasswordSetupToken`), nueva migración `add_password_setup_tokens`.
- **Backend `src/modules/auth/`**: nuevo puerto `PasswordSetupTokenRepository` + implementaciones Prisma/InMemory, nuevos casos de uso (`IssuePasswordSetupTokenUseCase`, `SendSetPasswordEmailUseCase`, `CompletePasswordSetupUseCase`), cambios en `LoginUseCase`, `UserRepository` (nuevo método `updatePasswordHash`), `AuthController`, DI container.
- **Backend `src/modules/users/`**: `CreateAdminUserUseCase`, `CreateUserRequest`, `AdminUserRepository`, `UsersController` (schema Zod + nuevo endpoint), DI container.
- **Rutas Next.js**: `app/api/v1/auth/set-password/route.ts` (nueva), `app/api/v1/admin/users/[id]/resend-set-password-email/route.ts` (nueva).
- **Middleware**: `AuthMiddlewareAdapter` — nuevas rutas públicas `/api/v1/auth/set-password` y `/auth/set-password`.
- **Frontend**: `UserEditModal.tsx`, `_logic/schemas/createUser.schema.ts`, `_logic/types/api.ts`, `_logic/services/createUser.ts`, nuevo `_logic/services/resendSetPasswordEmail.ts`, `useUserMutations.ts`, `UsersPage.tsx`, nueva página pública `app/(public)/auth/set-password/`, ajuste en la lógica de login para el caso `PasswordNotSet`.
- **Env**: nueva variable `APP_URL` en `.env.example` (base para el link del correo).
- **Dependencias externas**: ninguna nueva — reutiliza `nodemailer` (ya instalado) y `bcryptjs`/`jsonwebtoken` ya usados por `auth`.
