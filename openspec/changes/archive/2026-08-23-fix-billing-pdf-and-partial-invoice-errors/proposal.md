## Why

Los servicios frontend de facturación (`app/(private)/billing/_logic/services/`) violan hoy el requirement vigente "Typed services and error normalization" (`billing-ui`): `downloadInvoicePreviewPdf.ts` y `stampInvoice.ts` sólo reconocen un shape de error 400 (`ReceiverFiscalDataIncomplete`) y colapsan cualquier otro 400 del backend a un `NetworkError` genérico, ocultando la causa real. Esto produce dos síntomas reportados por el usuario ("error al generar prefactura en pdf" y "error al crear factura parcial") que en realidad son dos causas raíz distintas y ya diagnosticadas por código:

1. **Prefactura PDF**: `getInvoicePreviewSource.ts` adapta el DTO real de venta (`SaleItemDto`, que declara `discountPct`/`ivaRate`/`iepsRate` como `number | null`) a un tipo interno que promete no-nullable, sin normalizar — el `null` llega intacto al POST y el schema Zod del backend (`previewLineSchema`) lo rechaza con 400, que el cliente traduce a "Network error".
2. **Factura parcial**: dos disparadores reales de 400 no manejados — `BranchRequired` (sin sucursal matriz configurada) y errores de validación Zod sobre `satProductCode` capturado a mano en líneas libres (formato exigido `^\d{8}$`, el input UI sólo limita `maxLength={8}` sin mínimo).

Adicionalmente se detectó un tercer defecto en el mismo componente de PDF (`InvoiceDocumentPdf.tsx`): la función `pct()` asume escala 0–1 para todo, pero `discountPct` usa escala 0–100 en todo el sistema (ver fórmula documentada en `CLAUDE.md` § "Cálculo de totales") — infla el descuento mostrado ×100.

## What Changes

- **`getInvoicePreviewSource.ts`**: normaliza explícitamente `discountPct`/`ivaRate`/`iepsRate` de cada línea de venta a `?? 0` al adaptar el DTO real del API, en vez de la asignación directa que hoy le miente al tipo declarado.
- **`downloadInvoicePreviewPdf.ts`**: distingue 400 y expone el mensaje real del backend en vez de colapsar a `NetworkError` genérico.
- **`BillingController.previewPdf`**: agrega `try/catch` alrededor de `renderToBuffer(...)`, igual patrón que el resto de handlers del controller (`stamp`, `cancel`, `download`, `email`, `uploadCsd`), devolviendo un 500 con body JSON en vez de una excepción no manejada.
- **`InvoiceDocumentPdf.tsx`**: corrige el cálculo de `discountPct` en el PDF para usar su escala real (0–100), sin afectar el cálculo de `ivaRate`/`iepsRate` (escala 0–1, sin cambio).
- **`errors.ts` (billing frontend)**: agrega `BranchRequiredError`, siguiendo el mismo molde que los demás errores tipados del módulo.
- **`stampInvoice.ts`**: reconoce el 400 `BranchRequired` → `BranchRequiredError`; para cualquier otro 400 no reconocido (Zod `fieldErrors`), expone un mensaje legible derivado del error del backend en vez de `NetworkError` genérico.
- **`PartialInvoiceLineRow.tsx`**: valida el input de `satProductCode` antes de submit (bloquea o advierte si el valor no está vacío y no son exactamente 8 dígitos), previniendo el 400 en vez de sólo mejorar su mensaje.

### Modified Capabilities
- `billing-api`: el requirement "Invoice preview PDF endpoint" se aclara para exigir que el body acepte líneas con `discountPct`/`ivaRate`/`iepsRate` nulos normalizados a `0` en vez de rechazarlos, y que un fallo interno del renderer devuelva un error 500 con body JSON tipado en vez de una excepción no manejada.
- `billing-ui`: el requirement "Typed services and error normalization" gana `BranchRequiredError` a la lista de errores tipados y la obligación explícita de no colapsar 400s no reconocidos a `NetworkError`. El requirement "Partial standalone invoice" gana la validación de formato de `satProductCode` antes de submit. El requirement "Invoice preview before stamping" se aclara: el mensaje de "Download failure shown inline" debe reflejar la causa real del backend, no un mensaje genérico.

- **Archivo nuevo**: `app/(private)/billing/_logic/services/_errorMessage.ts` (helper compartido para derivar un mensaje legible de un body de error 400, usado por `downloadInvoicePreviewPdf.ts` y `stampInvoice.ts`).
- **Sin archivos nuevos**, sin migración de BD, sin cambio de contrato de API público (los códigos de error `BranchRequired` y los `fieldErrors` de Zod ya existen en el backend hoy — sólo se reconocen del lado del cliente).
- **Sin impacto en permisos**: ningún gating (`billing:write`, branch scoping) se toca.
- **Riesgo bajo**: cambios de manejo de errores + una corrección de normalización de datos + una corrección de fórmula de presentación — no altera flujos de timbrado real ni persistencia.
