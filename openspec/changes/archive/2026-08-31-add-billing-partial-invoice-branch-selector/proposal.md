## Why

El fix archivado `2026-08-30-fix-billing-invoice-price-branch-scope` igualó los dos call sites de `getProductPrices` en `PartialInvoiceForm` para que ambos usaran `effectiveBranchId = branchId ?? hq?.id ?? null`. El código de ese fix está correctamente aplicado, pero no resuelve el problema real para el rol que más lo sufre: un usuario con `branches:access_all` (admin) cuyo `branchId` propio es `null` y para quien, en esta base de datos, **ninguna sucursal está marcada `is_headquarters=true`**. En ese caso `effectiveBranchId` es `null` con o sin el fix, `getProductPrices` se llama sin `branchId`, el backend (`findByProductId`) sólo devuelve precios globales, y como la mayoría de productos reales sólo tienen precio branch-scoped (post migración `add-branch-scoped-prices`), la línea queda en `$0.00` y "Elegir precio" muestra "Este producto no tiene precios configurados." — verificado en vivo con Playwright usando `admin@example.com` con sesión fresca.

El proposal anterior ya documentaba este caso límite como "sin regresión" (es decir, deliberadamente sin arreglar), sin notar que es precisamente el caso de uso más común para el rol admin en un entorno donde aún no se ha configurado una sucursal matriz.

La causa raíz de fondo es que `NewInvoicePage.tsx` pasa el `branchId` del usuario directo a `PartialInvoiceForm` sin ofrecer ningún mecanismo para que un usuario bypass elija una sucursal — a diferencia de `PosPage.tsx`, que ya resuelve exactamente este mismo problema (resolución de precios de catálogo por sucursal) con un selector de sucursal visible sólo para `branches:access_all`, poblado desde `GET /admin/branches`, sin autoselección (el usuario debe elegir explícitamente). Replicar ese patrón ya probado en producción evita depender de la configuración de HQ (que puede no existir) y da control explícito al admin sobre qué catálogo de precios está consultando.

## What Changes

- `PartialInvoiceForm.tsx` (o `NewInvoicePage.tsx`, a decidir en `design.md`) gana un selector de sucursal, visible únicamente cuando `can("branches:access_all") === true`, siguiendo el mismo patrón ya implementado en `PosPage.tsx`:
  - Usuario con `branches:access_all`: lista completa de sucursales activas vía `GET /admin/branches?pageSize=100&includeInactive=false`; sin autoselección — arranca vacío, igual que POS.
  - Usuario sin `branches:access_all` con `branchId` propio: sin selector visible, comportamiento actual sin cambios.
- `effectiveBranchId` deja de depender de `useHeadquarters()` como fallback y pasa a derivarse de: `branchId` propio (no-bypass) **o** la sucursal explícitamente seleccionada en el nuevo selector (bypass) — mismo criterio que `selectedBranchId` en `PosPage`.
- Ambos call sites existentes de `getProductPrices` en `PartialInvoiceForm` (`handleAddProduct`, `handleChangeTier`) usan el nuevo `effectiveBranchId` — se mantiene la paridad entre ambos que ya garantizó el fix anterior, sólo que ahora el valor puede resolver a una sucursal real para admins sin `branchId`/HQ.
- Se retira la dependencia de `useHeadquarters()` en `PartialInvoiceForm` (queda sin uso tras este cambio, salvo que otro requirement la siga necesitando — a confirmar en `design.md`).
- Cobertura de test: caso bypass con selector cambiando de sucursal, caso no-bypass sin selector visible, y regresión del caso "sin sucursal resuelta" (comportamiento sin cambios).
- Verificación en vivo obligatoria (Playwright + servidor dev + DB real de este entorno) reproduciendo el mismo producto/sucursal usados en el diagnóstico, antes de dar el cambio por terminado.
